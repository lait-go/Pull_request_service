# Pull Request Reviewer Assignment Service

Сервис назначения ревьюеров для Pull Request'ов (Тестовое задание для стажёра Backend, осенняя волна 2025).

## 🚀 Быстрый запуск

```bash
docker-compose up
```

Сервис будет доступен на `http://localhost:8080`

Миграции применяются автоматически при запуске.

## Описание

Микросервис для автоматического назначения ревьюеров на Pull Request'ы, управления командами и участниками. Взаимодействие происходит исключительно через HTTP API.

### Основной функционал

- **Автоматическое назначение ревьюверов**: При создании PR автоматически назначаются до 2 активных ревьюверов из команды автора (исключая самого автора)
- **Переназначение ревьюверов**: Замена одного ревьювера на случайного активного участника из команды заменяемого ревьювера
- **Управление командами**: Создание и обновление команд с участниками
- **Управление активностью пользователей**: Установка флага активности пользователей
- **Защита от изменений**: После MERGED изменение состава ревьюверов запрещено
- **Идемпотентность**: Операция merge идемпотентна - повторный вызов не приводит к ошибке

## Архитектура

Проект следует принципам Clean Architecture (DDD):
- **Domain** - доменные модели и ошибки
- **Usecase** - бизнес-логика, независимая от HTTP
- **Adapters** - адаптеры для работы с БД (PostgreSQL)
- **Controllers** - HTTP handlers, адаптеры между HTTP и usecase слоем

## API Endpoints

API соответствует OpenAPI спецификации (`openapi.yml`):

### Teams

- `POST /team/add` - Создать или обновить команду с участниками
  - Ответ: `{team: Team}` (201 Created)
- `GET /team/get?team_name=<name>` - Получить команду с участниками
  - Ответ: `Team` (200 OK)

### Pull Requests

- `POST /pullRequest/create` - Создать PR (автоматически назначает до 2 ревьюверов)
  - Ответ: `{pr: PullRequest}` (201 Created)
- `POST /pullRequest/merge` - Пометить PR как MERGED (идемпотентная операция)
  - Ответ: `{pr: PullRequest}` (200 OK)
- `POST /pullRequest/reassign` - Переназначить ревьювера
  - Ответ: `{pr: PullRequest, replaced_by: string}` (200 OK)

### Users

- `GET /users/getReview?user_id=<id>` - Получить PR'ы, где пользователь ревьювер
  - Ответ: `{user_id: string, pull_requests: []PullRequestShort}` (200 OK)
- `POST /users/setIsActive` - Установить флаг активности пользователя
  - Ответ: `{user: User}` (200 OK)

## Особенности реализации

- **Clean Architecture**: Разделение на слои (domain, usecase, adapters, controllers)
- **Обработка ошибок**: Централизованная обработка доменных ошибок
- **Транзакции**: Все операции с БД выполняются в транзакциях
- **Middleware**: Recovery, Request ID, Logging
- **Идемпотентность**: Операции мержа PR идемпотентны
- **Автоматическое назначение**: До 2 ревьюверов назначаются автоматически из команды автора
- **Случайный выбор**: Ревьюверы выбираются случайным образом из доступных активных участников команды

## Бизнес-правила

1. При создании PR автоматически назначаются до 2 активных ревьюверов из команды автора (исключая самого автора)
2. Если доступных кандидатов меньше двух, назначается доступное количество (0/1)
3. Пользователь с `isActive = false` не назначается на ревью
4. Переназначение заменяет одного ревьювера на случайного активного участника из команды заменяемого ревьювера
5. После MERGED менять список ревьюверов нельзя
6. Операция merge идемпотентна - повторный вызов не приводит к ошибке

## Вопросы и допущения

### Вопросы, на которые не было ответов в ТЗ

1. **Статус коды для создания команды**: 
   - **Решение**: Использую 201 Created для создания новой команды, так как это соответствует RESTful практикам. При обновлении существующей команды также возвращается 201, так как `CreateOrUpdateTeam` может как создавать, так и обновлять.

2. **Обработка пустых команд**:
   - **Решение**: Разрешаю создание команд без участников. При создании PR с автором из такой команды PR будет создан без ревьюверов (0 ревьюверов), согласно ТЗ: "Если доступных кандидатов меньше двух, назначается доступное количество (0/1)".

3. **Валидация входных данных**:
   - **Решение**: Базовая валидация выполняется на уровне handlers (проверка JSON), более сложная валидация - в usecase слое.

4. **Обработка дублирующихся пользователей в команде**:
   - **Решение**: Разрешаю дублирующиеся `user_id` в списке участников команды при создании/обновлении. Последний указанный пользователь будет использован.

5. **Переназначение ревьювера из команды автора или из команды ревьювера**:
   - **Решение**: Согласно ТЗ, переназначение происходит из команды заменяемого ревьювера, что и реализовано. Новый ревьювер выбирается из команды старого ревьювера, исключая автора PR и самого старого ревьювера.

6. **Создание PR без активных кандидатов**:
   - **Решение**: Согласно ТЗ "Если доступных кандидатов меньше двух, назначается доступное количество (0/1)", если активных кандидатов 0, PR создается без ревьюверов (0 ревьюверов), а не возвращает ошибку.

## Troubleshooting

### Проблемы с подключением к БД

1. Убедитесь, что PostgreSQL запущен:
   ```bash
   docker-compose up db
   ```

2. Проверьте строку подключения в `.env` или переменной окружения `DB_SOURCE`

3. Проверьте доступность БД:
   ```bash
   psql "postgres://user:password@localhost:5432/dbname"
   ```

### Проблемы с тестами

1. Убедитесь, что тестовая БД доступна
2. Проверьте переменную `TEST_DB_SOURCE`
3. Для интеграционных тестов БД должна быть пустой или будет очищена автоматически

### Проблемы с API тестами

1. Убедитесь, что приложение запущено:
   ```bash
   docker-compose up
   # или
   make run
   ```

2. Проверьте URL в переменной `API_URL` (по умолчанию `http://localhost:8080`)

3. Убедитесь, что `jq` установлен (для форматирования JSON в тестах):
   ```bash
   # macOS
   brew install jq
   
   # Ubuntu/Debian
   sudo apt-get install jq
   ```
